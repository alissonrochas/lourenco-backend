## 1. Resumo executivo

**Avaliação: não pronto para produção neste momento.** As funcionalidades principais e a integridade transacional passaram nas verificações executadas, mas há bloqueadores de disponibilidade/recuperação e decisões de deploy ainda sem evidência. Não foi demonstrado acesso administrativo sem autorização nem quebra criptográfica de sessão.

Foram registrados **17 achados: P0=0, P1=5, P2=10, P3=2**. A classificação inclui problemas confirmados, riscos condicionais e melhorias; não representa 17 vulnerabilidades exploráveis remotamente. Os P1 são R01–R05: persistência fora de releases, backup/restauração, crescimento não limitado do rate limiter, abuso de reservas e configuração verificável de transporte/proxy/cookies. R01/R02/R05 são condicionais à implantação, ainda não fornecida; podem ser encerrados com evidências operacionais adequadas, sem presumir que um servidor real esteja configurado incorretamente.

Os cinco riscos mais relevantes são: perder o SQLite num rebuild/deploy efêmero; não recuperar reservas após falha; esgotar memória mesmo com logins recebendo 429; ocupar a agenda com reservas não verificadas; e implantar frontend/API com TLS, cookies, origem ou proxy incompatíveis. SQLite continua adequado ao MVP de uma barbearia em um único host; a auditoria não justifica migração automática para PostgreSQL.

## 6. SQLite, integridade, migrations e recuperação

O caminho é app.tmpPath('db.sqlite3') fora de NODE_ENV=test; a suíte normal exige :memory: antes das migrations. No runtime do build, tmp é relativo à raiz do artefato. O assembler limpa o diretório build. A prova colocou um SQLite-sentinela exclusivamente em build/tmp de um checkout descartável: o build o removeu. Portanto um deploy que compile dentro do runtime ou deixe o arquivo em release/FS efêmero pode perder reservas (R01). Não foi tocado o banco original. [config/database.ts:14](https://github.com/alissonrochas/lourenco-backend/blob/15fda381bd1faa83775b7fe59f2f0cc41a74abd0/config/database.ts#L14), [package.json:12](https://github.com/alissonrochas/lourenco-backend/blob/15fda381bd1faa83775b7fe59f2f0cc41a74abd0/package.json#L12), [tests/bootstrap.ts:36](https://github.com/alissonrochas/lourenco-backend/blob/15fda381bd1faa83775b7fe59f2f0cc41a74abd0/tests/bootstrap.ts#L36).

Constraints verificadas pelas migrations reais: FKs RESTRICT, status, números inteiros, data local, duração exata de 3.600.000 ms, auditoria consistente e índice único parcial de início UTC para confirmed. Transações serializam escritores antes das leituras decisivas; falhas revertem também criação de cliente. [database/migrations/1795824000000_create_bookings_table.ts:1](https://github.com/alissonrochas/lourenco-backend/blob/15fda381bd1faa83775b7fe59f2f0cc41a74abd0/database/migrations/1795824000000_create_bookings_table.ts#L1).

Na conexão descartável medida: SQLite **3.54.1**, foreign_keys=1, journal_mode=delete, busy_timeout=5000 ms, synchronous=2. O timeout vem do driver instalado; não confundir ausência de configuração explícita com timeout zero ou FKs desligadas. A leitura de flags usa uma conexão equivalente do mesmo driver, não o banco de produção. A configuração da aplicação não define WAL; operações sob contenção podem ocupar o event loop do driver síncrono até o timeout. WAL é uma avaliação de desempenho, não requisito automático de segurança nem suporte a múltiplos escritores simultâneos. Não foi feito benchmark prolongado.

Há migrations aditivas e testes reais de aplicação/rollback. Backfill de telefone executa via this.defer; primeiro ID válido recebe phone_normalized e equivalentes/ inválidos permanecem nulos. ## 11. Deploy recomendado e variáveis

Uma única VM/host com SSD local persistente; proxy TLS (Nginx ou equivalente), dist da SPA na mesma origem, /api encaminhado ao Node em loopback e um processo Node supervisionado. Não expor Vite dev/preview, o porto Node nem páginas legadas do backend pela regra genérica da SPA. /admin recebe fallback index.html; /api preserva status/JSON, cookies e ETag/If-Match. O volume de dados deve ficar fora dos releases; construir em CI/diretório separado e promover artefato, nunca rebuild dentro do runtime com dados. Usuário de sistema dedicado, mínimo acesso ao diretório de dados/backups, patches e relógio sincronizado. Não são necessários Kubernetes, Redis ou cluster de banco para o volume informado.

Preferir mesma origem: cookies são host-only (domain vazio) e o cliente lê XSRF-TOKEN via document.cookie. Colocar SPA e API em subdomínios diferentes com os defaults faz o cookie XSRF do host API ficar ilegível no host SPA; habilitar CORS não muda isso. Não resolver desabilitando CSRF. Um proxy de mesma origem evita mudanças globais de domínio de cookie. [Cookies/Domain](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Set-Cookie), [config/app.ts:56](https://github.com/alissonrochas/lourenco-backend/blob/15fda381bd1faa83775b7fe59f2f0cc41a74abd0/config/app.ts#L56), [frontend/src/lib/api.ts:78](https://github.com/alissonrochas/lourenco-frontend/blob/0af252f9191b625cdfbbc3500305604b20008d86/src/lib/api.ts#L78).

## 14. CI/CD proposto — não implementado

Não há workflows .github/workflows versionados nos dois HEADs. Isso não prova ausência de CI externo ou de proteção de branch; ambas precisam ser verificadas pelo proprietário. Não foram criados workflows nesta fase (R14).

- Frontend: pull_request/push main; Node compatível com o projeto; npm ci; lint; typecheck; npm test; build. Cache apenas do download npm por OS/Node/lock, não de binários nativos/node_modules entre plataformas.
- Backend: npm ci e etapa de geração de índices necessária ao checkout limpo (o build atual a executa); lint; typecheck completo; unitários+funcionais em SQLite de teste; build. Corrigir os oito erros antes de tornar a verificação obrigatória; não usar continue-on-error ou ignore-ts-errors para mascará-los.
- Integração: checkouts dos dois SHAs explícitos, Node/Chromium, dependências e harness real existentes. Mudanças coordenadas podem usar workflow_dispatch com par de SHAs aprovado; após merge backend, frontend testa contra aquele contrato. Não depender implicitamente de branch móvel.
- Permissões contents:read; sem chaves de produção, sem seed de produção, sem deploy no job de PR. Não executar código de fork com segredos via pull_request_target. Pinar actions e limitar retenção de artefatos de falha (por exemplo sete dias), com dados fictícios; traces podem conter cookies de teste.
- Uma execução sequencial e um worker Playwright são suficientes inicialmente. O recorte completo local levou cerca de três minutos de E2E; instalação em runner aumenta esse tempo. Não é necessário cluster de testes. Gate de review e smoke de staging antes de publicação manual, com rollback de artefato que preserve dados e schema.
